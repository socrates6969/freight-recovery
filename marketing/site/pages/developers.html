For developers: what the API can do today

The platform has a programming interface for machine clients. This page describes it as it is built today, including what a key cannot do. There is no public endpoint yet: nothing is deployed, and every example below uses placeholders.

Status: pre-product. The API runs only in our own test environment on synthetic data. No customer has an API key, and route names, limits and scopes can still change.

What a key can do today

Nine routes accept a tenant API key, each only with the matching scope. Every other route answers 403 to a key.

ScopeRoutesWhat it is for
imports.writeFive upload and batch routes under /api/v1/importsCreate an import batch and upload documents to it, one application/octet-stream body per file. Files are type-checked and parsed in a sandbox, then reviewed by a person before they become claims.
claims.readGET /api/v1/claims, GET /api/v1/claims/:id, GET /api/v1/claims/:id/documentsList and read claim summaries and the documents attached to a claim.
exports.claimsGET /api/v1/exports/claimsStream a CSV or XLSX export of claims, with spreadsheet formulas neutralised.

Current upload defaults: up to 10 files per batch and 10 MiB per file, with a parse timeout per file. They are configuration values, not published commitments.

How API keys and scopes work

  • Format: fr_live_<keyId>_<secret>. The secret is shown once, when the key is created; we store only a keyed hash (HMAC-SHA256 with a server-side pepper), never the secret itself.
  • Sending it: only in the Authorization header as a Bearer token. Other headers are not read as keys.
  • Who issues keys: a tenant's OWNER or ADMIN creates, lists and revokes keys in the app or through /api/v1/api-keys. Each key carries one or more scopes and an optional expiry date.
  • Scopes: a key opens only the routes of the scopes it holds. Creating keys, approving findings and every other administrative or decision route stay closed to keys.
  • Tenancy: a key belongs to one tenant and sees only that tenant's data.
curl -H "Authorization: Bearer fr_live_<keyId>_<secret>" \
     https://<host>/api/v1/claims

The host is a placeholder: there is no public base URL yet.

Errors and rate limits

  • 401: a missing, invalid, revoked or expired key. All of these answer with the same body, so a response never reveals which keys exist.
  • 403: the route is not open to keys, or the key lacks the scope.
  • Error body: {"error": {"code", "message", "requestId", "details?"}} with a stable, machine-readable code. Validation errors list field paths, never the values you sent.
  • 429: rate limits apply per address, per route group and per key, and a 429 response carries Retry-After. The numbers are not published, because pricing has not fixed them.

What a key cannot do yet

An integration can push documents and read claim summaries. It cannot trigger an analysis, read an evidence packet or record a decision: those routes are open only to signed-in people today. Approving, rejecting and marking a packet ready to send need a second person who did not prepare it, and they will stay human-only. Whether a scope should open packet reads and analysis is an open design question.

There are no TMS, ERP or accounting integrations, no SDK and no webhooks.

Developer portal status

The developer portal is built but not hosted, so there is nothing to link to yet. It currently documents an earlier Python reference service, which uses a different key format, header and error shape from the API described on this page. We are regenerating it from the API's own request and response schemas, as an OpenAPI 3.1 document, starting with the nine routes that accept keys. Until then, this page is the summary we stand behind.
