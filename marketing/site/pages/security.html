Security status

Customers would give us contracts, rates, invoices and shipment records, and our findings would be used to claim money from other companies. So we would rather tell you what is missing than imply a posture we do not have.

Real customer data is not accepted until the items under "Not yet" are done.

Built into the platform

  • Tenant isolation in the database. Row-level security is forced on every customer table, and every query runs inside a transaction bound to one customer, so a bug in application code cannot read another customer's data. The runtime database role cannot bypass it.
  • Roles re-checked on every request. A user's role and customer account are read from the database each time, never trusted from a token or a request header.
  • Four-eyes approval. The person who created a claim, edited its source data, or wrote a charge label that influenced it cannot approve it. The rule is enforced in the application and again by database triggers.
  • Tamper-evident audit log. Every action is appended to a hash-linked log; evidence packets carry a content hash.
  • Sign-in protection. Argon2id password hashing, multi-factor sign-in for privileged roles, rotating refresh tokens with reuse detection, lockout after repeated failures (including on password change), and sessions revoked when a user is promoted to a role that requires multi-factor sign-in they have not set up.
  • API keys stored only as keyed hashes, scoped, rate-limited and revocable.
  • Isolated document parsing. Uploads are parsed in separate worker processes with time, memory and size limits and no network access. File names and storage keys are generated by the server.
  • Abuse limits. Per-user and per-address rate limits, request size limits and bounded lists. Behind the planned CDN, the real client address is only trusted when the request carries a secret that only the CDN knows.
  • Secrets never in code or logs; production refuses to start with missing, weak or placeholder secrets.
  • Change process. Each change goes through a written specification, implementation, tests written from a separate specification, a security review and a final review. These reviews are performed by separate AI review agents with fixed instructions, supervised by the founder. The most recent round found and closed one medium and several low issues before merge.
  • Infrastructure as code for private networking, encryption at rest and TLS-only traffic. It is checked automatically but has not been deployed.

Not yet

  • Independent third-party security assessment or penetration test. No human outside the company has reviewed the code.
  • Any compliance certification or attestation.
  • Malware scanning of uploads.
  • Production hosting, and a tested incident response plan.
  • A data retention and deletion policy.
  • Reviewed legal terms (our privacy, terms and cookie pages are drafts).

Known open items from our own reviews are tracked in the project's threat model and will be closed before the first customer deployment.
